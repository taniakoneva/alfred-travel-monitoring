# 01. Требования и допущения

## Контекст

TravelTech-сервис планирует поездки: билеты, отели, трансферы, активности. Все бронирования собраны в одном плане. Задача: сделать подсистему «Альфред», которая следит за рейсами, предупреждает о задержках и отменах, предлагает замену и обновляет общий план.

## Пользователи

| Роль | Что делает |
| --- | --- |
| Путешественник | Получает уведомления, выбирает вариант замены |
| Организатор группы | Принимает решения за всех участников |
| Участник группы | Видит общий план и свои уведомления |

## Цель

Человек узнаёт о проблеме с рейсом раньше, чем заметит её сам, и сразу получает готовые варианты, а общий план поездки остаётся актуальным и согласованным.

## Функциональные требования

| ID | Требование |
| --- | --- |
| FR-1 | Система отслеживает статусы рейсов из планов поездок через внешние API и рассылки авиакомпаний |
| FR-2 | При значимом изменении (задержка, отмена, замена рейса) система уведомляет затронутых путешественников |
| FR-3 | Система находит затронутые поездки и сегменты плана: стыковки, трансфер, отель |
| FR-4 | Система предлагает до трёх альтернативных рейсов, прошедших проверки багажа, виз, таймзон и мест |
| FR-5 | Билеты меняются только после явного выбора пользователя (в группе: организатора) |
| FR-6 | После выбора система перебронирует рейс и сохраняет новую версию общего плана, сдвигая трансфер и отель |
| FR-7 | Если авиакомпания сама перебронировала пассажира, система переносит это решение в план и показывает, что изменилось |
| FR-8 | Паспортные данные хранятся только на время поездки и удаляются автоматически |

## Нефункциональные требования

| ID | Требование |
| --- | --- |
| NFR-1 | Уведомление уходит не позже чем через 1 минуту после подтверждённого значимого изменения |
| NFR-2 | Если внешний источник недоступен, пользователь видит последние данные и время их обновления, события не теряются |
| NFR-3 | Повторная доставка одного и того же события не приводит к повторным уведомлениям |
| NFR-4 | Копия плана доступна в приложении без сети |
| NFR-5 | Паспортные данные шифруются, доступ к ним ограничен, другим сервисам передаётся токен |

## Допущения

- Статусы рейсов берём у агрегатора (например, FlightAware) и из рассылок авиакомпаний.
- Поиск и перебронь идут через API авиакомпаний и GDS.
- Все времена хранятся в UTC вместе с таймзоной аэропорта, пользователю показывается местное время аэропорта.
- Интервалы опроса источников (ниже) примерные: на практике они зависят от лимитов API и возможностей поставщика.

## Вне рамок

Оплата и платёжный шлюз (используем готовый), рекомендации и персонализация, отзывы после поездки. Эти процессы есть в сервисе, но к заданию не относятся.
