# 05. Ограничения и исключительные сценарии

## Сводная таблица

| Ограничение | Решение |
| --- | --- |
| Данные о рейсах приходят с задержкой | Храним время события у источника и применяем только более свежие. Ближе к вылету опрашиваем чаще, например: за сутки раз в 15 минут, за 3 часа раз в 5 минут. Интервалы примерные и зависят от лимитов API поставщика |
| Источники противоречат друг другу | Отмену перепроверяем во втором источнике, прежде чем предлагать перебронь |
| Пользователь оффлайн | Уведомление сначала сохраняется в базу и ждёт доставки. Критичное через 10 минут дублируем SMS. В приложении есть копия плана, доступная без сети |
| Багаж | Норма багажа в новом варианте не меньше исходной. Если багаж придётся забрать и сдать заново, закладываем на это время |
| Визы | Проверяем транзитные визы по каждому участнику (подробности ниже). Вариант, где нужна отсутствующая виза, не показываем |
| Таймзоны | Сравниваем время только в UTC, пользователю показываем местное время аэропорта |
| Групповая поездка | Предлагаем варианты, где хватает мест на всех. Решение принимает организатор |
| Отказ внешнего API | Повторяем запрос с паузой, переключаемся на резервный источник, показываем время последнего обновления |
| Паспортные данные | См. раздел ниже |

## 1. Устаревшие и повторные события

Пример: в 12:00 авиакомпания сообщает о задержке на 40 минут, в 12:03 агрегатор присылает задержку на 20 минут, в 12:05 приходит старое сообщение «по расписанию». Если применять всё подряд, пользователь увидит неверное время.

Правила:

1. У каждого события хранятся время у источника (`source_updated_at`) и время получения (`received_at`).
2. Событие, более старое, чем уже применённое, не применяется.
3. У события есть уникальный ключ (например, источник + рейс + статус + `source_updated_at`). Повторная доставка с тем же ключом игнорируется, поэтому повторных уведомлений не будет.

Это называется идемпотентностью обработки и контролем порядка событий.

## 2. Версии плана и конфликт изменений

Общий план имеет версию:

- версия 1: первоначальный план;
- версия 2: обнаружена задержка, предложены альтернативы;
- версия 3: пользователь выбрал новый рейс, обновлены трансфер и заселение.

Правило сохранения: изменение принимается, только если версия, на которой оно основано, совпадает с текущей. Это называется оптимистической блокировкой.

Если пользователь сам изменил трансфер, а система одновременно хочет сдвинуть его из-за задержки, система не перезаписывает чужую правку молча. Она перечитывает план, показывает, что изменилось, и просит подтвердить итог.

## 3. Подбор альтернатив: два этапа

**Этап 1. Обязательные проверки (фильтрация).** Вариант, не прошедший хотя бы одну проверку, не показывается:

- подходит по визовым требованиям каждого участника;
- хватает мест для всей группы;
- багаж не хуже исходного;
- пересадка реалистична (см. ниже);
- вариант не ломает другие сегменты маршрута: трансфер, отель.

**Этап 2. Ранжирование.** Среди прошедших отбираем три лучших по времени прибытия, числу пересадок и доплате (при равенстве можно учитывать удобство маршрута).

Вариант с более ранним прибытием, но невозможной пересадкой или отсутствующей визой не попадает в список вообще.

**Визы.** Проверка не сводится к гражданству. Значение могут иметь страна и аэропорт транзита, нужно ли выходить из транзитной зоны, оформлены ли рейсы одним билетом или отдельными. Если данных недостаточно, вариант показывается с пометкой «требует дополнительной проверки» и ниже подтверждённых, а не выдаётся за гарантированно допустимый.

**Реалистичность пересадки** определяется так:

- время между прибытием и вылетом не меньше минимального времени пересадки для аэропорта и типа маршрута плюс запас на непредвиденное;
- учтены смена терминала или аэропорта;
- учтена повторная регистрация багажа, если она нужна;
- учтены визовые ограничения;
- время считается в UTC, чтобы не ошибиться из-за смены часовых поясов.

## 4. Авиакомпания сама перебронировала пассажира

При отмене авиакомпания нередко сама назначает новый рейс. Система должна учитывать не только свои действия, но и изменения во внешних системах.

1. Система получает уведомление об отмене рейса.
2. Пользователю уходит уведомление.
3. Позже авиакомпания самостоятельно назначает новый рейс.
4. Система получает обновлённые данные.
5. Система проверяет новый рейс на совместимость с остальным маршрутом.
6. Если всё подходит, обновляет план (новая версия) и сообщает, что изменилось.
7. Если новый рейс конфликтует с трансфером, отелем или другими сегментами, система предлагает варианты решения.

В любом случае свои варианты в этот момент не навязываются. Пользователь может отказаться от решения авиакомпании и запросить другие варианты.

## 5. Паспортные данные

Принцип: хранить как можно меньше и как можно короче.

- Паспортные данные лежат отдельно от остальных данных пользователя, в зашифрованном виде.
- Доступ только у компонентов, которым они нужны для конкретной операции (оформление и перебронь).
- Другим сервисам передаётся токен документа, а не сами данные. Доступ к связи «токен → документ» тоже ограничен: токенизация сама по себе не делает данные анонимными.
- Дата удаления записывается в сущность «Документ», удаление выполняется автоматически.
- Срок: через 24 часа после окончания поездки. Данные могут понадобиться для перебронирования и регистрации прямо во время поездки, поэтому раньше удалять нельзя. 24 часа остаются как запас на завершающие операции. Срок настраивается, и если закон или договор требуют иного, действует он.
- Если поездка отменена, данные удаляются сразу.
- Если из-за перебронирования дата окончания сдвинулась, дата удаления пересчитывается при сохранении новой версии плана.
